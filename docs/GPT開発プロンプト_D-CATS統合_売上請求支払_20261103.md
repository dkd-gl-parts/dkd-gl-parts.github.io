# D-CATS 売上・請求・入金・支払 開発プロンプト（統合・一括リリース版） 2026-11-03

このドキュメントは、GPT（および任意のコーディングAI）に渡して、**D-CATS に受注以降の機能（売上・請求・入金・支払）を組み込み、機能フラグで隠して開発し、全機能がそろってから一括リリースする**ための、自己完結した指示書である。

## 0. 方針と前提（最重要）

- **別アプリ（単体版）は作らない。** 既存の D-CATS に機能を追加する。
- **開発は段階的、リリースは一括。** 各機能は**機能フラグで業務ユーザーに非表示のまま**本番に入れ、売上→請求→入金（→支払）が全部そろってから、一度にON にする。
- **稼働中の業務を混乱させない。** リリースまで現場は従来どおり受注のみを使い、売上以降は販売王で回し続ける。販売王は切替完了まで system of record。
- **逆アセンブル禁止。** 販売王の作りは SQL Server スキーマとして取得済み（第6章・関連資料）。実行ファイルの逆アセンブル・逆コンパイル・バイナリ解析は行わない。販売王の SQL Server へは**自社データの参照・移行目的でのみ**接続し、書き込まない。

## 1. D-CATS 開発ルール（`AGENTS.md` 準拠・厳守）

リポジトリ `dkd-gl-parts/dkd-gl-parts.github.io`（GitHub Pages、`dcats.daiko-denki.co.jp`）。DBは **Supabase (PostgreSQL)** プロジェクト `jqoeqximtwfpqwzngutj`。

- **作業用テーブルを `public` スキーマに作らない。** work/backup/staging/mapping/review/candidate/temp は `pg_temp` か `app_private` に。本番テーブルのみ `public`。
- **`app_private` のテーブルは、同じマイグレーションで RLS 有効＋deny-by-default にする。** `app_private` を Data API 公開スキーマに追加しない。ブラウザから private work テーブルへアクセスさせない。
- **秘密情報（DB資格情報・service-role key・管理トークン・決済情報）をリポジトリやブラウザコードに置かない。**
- **CSP は厳格に保つ。** inline script / inline style / `unsafe-inline` を再導入しない。
- **UIの権限チェックは利便性のみ。** 認可は RLS かレビュー済みサーバー関数で強制する。
- **売上・入金・請求・税・価格・在庫の最終確定はサーバー側でアトミックに実行する。** ブラウザ制御の多段書き込みにしない（Supabase RPC / Postgres 関数）。
- **mainへの変更は PR 経由。** `verify-search-workload` チェックが最新ブランチで通ること。force push / ブランチ削除不可。会話は解決してからマージ。
- D-CATS の作業スキル: スキーマ/RLS/関数の変更は `$dcats-change-database`、実装/検証/CSP/QA/リリースは `$dcats-release-frontend`、失敗リカバリは `$dcats-recover-development`。
- 変更は意図したファイルのみコミット。無関係な変更を混ぜない。

## 2. 作業方法のルール

- **git で1機能＝1ブランチ＝1 PR。** フォルダ複製でのバージョン管理は禁止（過去の失敗の反省）。
- 推測でスキーマを埋めない。**実機のSQLを根拠にする**（販売王・Supabase 両方を確認済み）。

- 請求の繰越・税の端数処理など、数字が合わないと作り直しになる箇所を最優先で固める。

## 3. 既にある土台（再利用する。作り直さない）

D-CATS Supabase に以下が本番稼働の形で存在する。金額は `integer`（円）、税率は `tax_rate_basis_points`（1000=10%）。

### 受注チェーン（完成済み）
```
customer_orders
 ├─ customer_order_items              明細（quantity / unit_price_jpy / line_total_jpy /
 │                                     discount_jpy / tax_rate_basis_points / tax_category_code /
 │                                     core_charge_jpy / core_return_handling）
 ├─ customer_order_stock_reservations 在庫引当
 ├─ customer_order_shipments          送り状（ヤマトB2）
 ├─ customer_order_dispatches         出荷指示
 │   ├─ customer_order_dispatch_items
 │   ├─ customer_order_dispatch_serials         製造シリアル割当
 │   └─ customer_order_dispatch_item_warranties 保証凍結
 ├─ customer_order_events
 └─ customer_order_b2_imports / _rows
```
`customer_orders` 主要列: order_number / sales_customer_id / status / subtotal_jpy / shipping_fee_jpy / tax_jpy / total_jpy / order_discount_jpy / shipping_tax_rate_basis_points / shipping_tax_type / selling_company_code / sales_channel / scheduled_shipping_date / shipped_on / completed_at / version / idempotency_key

### 請求マスタ（販売王から取込済み。ここが重要）
`sales_customers` に請求・回収設定が既にある:
`source_customer_code` / `billing_customer_code`(請求先) / `closing_code`(締めコード) / `collection_method_code` / `collection_month_offset` / `collection_day`(回収日) / `credit_limit_jpy`(与信) / `latest_ar_balance_jpy`(売掛残高) / `tax_method`(内税/外税) / `price_rank_code` / `customer_rate_multiplier` / `amount_adjustment_jpy` / `rounding_unit_jpy` / `rounding_method`

価格: `sales_price_ranks`(rate_multiplier / rounding_unit_jpy / rounding_method)、`product_base_prices` + `product_base_price_history`、`customer_shipping_rates`(送料)。
在庫: `core_product_variants` / `core_product_variant_stock_movements`。
仕入先: `suppliers` / `supplier_parts` / `internal_component_suppliers` / `manufacturing_cost_lists`。

→ **得意先・商品・在庫・受注・出荷・請求マスタは揃っている。欠けているのは売上以降の伝票だけ。**

## 4. 追加する機能（欠落分）

売上(sales_slips) / 請求(billing_statements) / 入金・消込(payment_receipts) / 売掛元帳(ar_ledger_entries)。必要に応じて仕入・支払（買掛側）。
**完全なDDL案は `docs/sales-billing-payment-design-20261103.md` の第4章にある。** 要点のみ:

- `sales_slips` / `sales_slip_items`（売上）: `customer_orders`/`customer_order_dispatches` から引継ぎ。`billing_customer_code`・`closing_code` を**計上時点で凍結**。slip_type(sale/return/adjustment)で赤伝対応。明細に原価単価（粗利）。インボイス登録番号を保持。
- `billing_statements` / `billing_statement_lines`（請求）: 繰越構造 **前回繰越 + 当期売上 − 当期入金 = 今回請求 → 残高**（販売王 `SkySmkr` と同構造・実機確認済み）。税率別内訳 jsonb、適格請求書発行事業者登録番号(T+13桁)。
- `payment_receipts` / `payment_receipt_allocations`（入金・消込）: 入金と充当を分離し、一部入金・複数請求充当・前受金・手数料差引・相殺を表現。
- `ar_ledger_entries`（売掛元帳）: 残高 = Σ(debit−credit)。`sales_customers.latest_ar_balance_jpy` はキャッシュ扱いで同期。
- 締めルール `closing_rules` を追加し、**販売王のマスタをそのままseed投入**（第4.5章）。得意先登録時はこの選択肢から選ぶ（販売王と同一運用）。

### 4.5 締め・回収ルール（販売王から確定。設計の推測不要）

締め区分・回収条件は販売王のマスタで定義済み。D-CATSはこれをseed投入し、得意先登録時の選択肢として使う（販売王と同一運用）。

**締めコード（販売王 `TkskShmGrp` → `closing_rules` にseed）**

| closing_code | 名称 | 締め方式 |
|---|---|---|
| 0 | 随時請求 | 締めなし・売上の都度請求 |
| 5 | ５日締め | 毎月5日 |
| 10 | １０日締め | 毎月10日 |
| 15 | １５日締め | 毎月15日 |
| 20 | ２０日締め | 毎月20日 |
| 25 | ２５日締め | 毎月25日 |
| 31 | 末日締め | 月末 |
| 50 | １５日／末日締め | 月2回（15日・末日） |

`closing_rules` の列案: `closing_code`(PK) / `name` / `closing_kind`(none/monthly/semimonthly) / `closing_days`(int[]、例 {31} や {15,31}) / `is_active`。

**回収方法（販売王 `KoteiKbn` → コードマスタにseed）**: 現金 / 振込 / 手形 / 振込手数料。

**得意先ごとの回収設定（販売王 `Tksk` → `sales_customers` に既存列あり）**
| 販売王 `Tksk` | 意味 | D-CATS `sales_customers` |
|---|---|---|
| `iTkskShmCd` | 締めコード | `closing_code` |
| `iKshShbts` | 回収種別（現金/掛） | `collection_method_code` |
| `iKshYoteiTsk` | 回収予定月（当月/翌月/翌々月） | `collection_month_offset` |
| `iKshYoteiDay` | 回収予定日 | `collection_day` |

**売上計上の起点（販売王方式に合わせる）**: 随時請求(closing_code=0)の得意先は売上の都度請求、それ以外は締め日で期間集計。D-CATSでは**出荷確定(`customer_order_dispatches`確定)時に売上を自動計上**し、`closing_code` で集計する。回収予定日は `collection_month_offset`/`collection_day` と締め日から算出。

**Supabase 実装の約束**
- 本番テーブルは `public`、RLS 有効。作業用は `app_private` または `pg_temp`。
- 売上計上・請求確定・入金消込・在庫更新は **Postgres 関数（RPC）としてサーバー側でアトミックに**。ブラウザ多段書き込み禁止。
- 既存慣習に合わせる: 金額 `integer`(円)、税率 `smallint` basis points、拡張は `jsonb`、楽観ロック用 `version`、冪等用 `idempotency_key`。

## 5. 機能フラグと一括リリース

- **フラグ設計**: 売上以降のメニュー・ルート・RPC を機能フラグ（例: `app_settings` のフラグ or ロール）で制御し、既定OFF。OFFの間、業務ユーザーには一切表示されず、呼べない（UI非表示＋RLS/サーバー関数でも拒否）。
- **開発中**: 本番に入れてもOFFなので業務は従来どおり。現場は受注のみ、売上以降は販売王。
- **一括リリース**: フェーズ1〜5（必要なら支払まで）完了・検証後、フラグを1回ONにして全機能を同時に公開。
- **権限で段階公開も可**: 先に管理者ロールだけONにして社内検証→全ユーザーON、も可能。業務影響は出さない。

## 6. 販売王 参照スキーマ（設計の裏取り。逆アセンブル不要）

販売王25 = SQL Server 2017 インスタンス `SORIMACHI2017`、DB `SPR25DB01`/`SPR25DB02`。命名は `業務略称+Dnpy/+DnpyMs`、ハンガリアン記法。
伝票対応: 見積`Mtsmr` / 受注`JchDnpy` / 売上`UrgDnpy` / 請求締`SkySmkr` / 入金`NyknDnpy` / 発注`HtchDnpy` / 仕入`ShirDnpy` / 支払締`ShharShmkr` / 支払`ShharDnpy`。
採るべき設計: ①ヘッダ+明細の2層 ②コードと名称を両方保存（凍結）③赤伝（確定は不変）④前工程からの明細レベル引継ぎ（分割納品）⑤請求締切が繰越計算を保存 ⑥インボイス登録番号を伝票に凍結 ⑦原価単価を明細に。
改善点: int日付→date型 / 予備枠カラム→jsonb / ローマ字略称→英語snake_case / money→integer / 粗い消込→receipt+allocation分離 / 残高の集計保存→元帳算出。

## 8. 税・締め・整合性の実装注意（請求が合わなくなる典型）

- **端数処理は伝票単位 × 税率別に1回だけ。** 明細ごとに丸めない。`sales_customers.rounding_unit_jpy`/`rounding_method` を適用。
- 内税/外税は `sales_customers.tax_method` に従い伝票に凍結。
- 締めは**冪等**（再実行で同じ請求書）。`idempotency_key` を使う。
- 売上計上は出荷確定と**同一トランザクション**。確定伝票はUPDATEせず赤伝で訂正。
- インボイス: 請求書に登録番号(T+13桁)と税率別の対価・消費税額を必須表示。

## 9. 販売王からのデータ移行

- SQL Server へは**参照接続のみ**。販売王稼働中に書き込まない。
- int日付(`iUrgDnpyDay`等)は `to_date(x::text,'YYYYMMDD')`。
- 得意先: 販売王 `Tksk.cTkskCd` ↔ `sales_customers.source_customer_code`（`source_code='hanbaiou'` が既に前提）。
- 売掛残高: `SkySmkr` の繰越残高を、移行開始日時点の `ar_ledger_entries` 期首エントリ1本として投入。
- 移行後、**得意先別の売掛残高が販売王と一致すること**を検証（最重要）。

## 11. レビュー依頼プロトコル（GPT → Claude／本番DB事故の防止）

本番DB（Supabase）へのマイグレーションは即反映されるため、**DBに効く変更は適用前にレビューを受ける**。GPTは各PRに次の形式でレビュー依頼を書く（人がPR番号をレビュアーに渡すことで成立する）。

PR本文テンプレート:
```
## 概要
<このPRで何を追加/変更したか>

## Claudeレビュー依頼
- [ ] マイグレーションDDL（本番適用前チェック）:
      <適用予定のDDL全文、または docs 内のパス>
- [ ] 確認してほしい点:
      <例: 税の端数処理が伝票単位×税率別で1回か / RLSがdeny-by-defaultか /
           publicに作業表を作っていないか / 請求繰越の式が §2.6 と一致するか>
- [ ] 販売王との数字突合が必要か: <はい/いいえ。はいなら対象（例: 得意先別売掛残高）>

## フラグ状態
<この変更は機能フラグOFFで業務非公開か>
```

ルール:
- マイグレーションを含むPRは、レビュー完了・承認まで**本番DBに適用しない**（コードのマージとDB適用を分けて扱う）。
- レビュアーは読み取り専用で検証する（販売王SQLは参照のみ、D-CATSコード/DBへは書き込まない）。
- GPTはレビュー指摘を次コミットで反映し、同じPRで対応する。
